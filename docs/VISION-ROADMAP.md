# SamePace delivery and remaining acceptance

The vision is a reliable workout community with actual fitness records, editable Jev assistance, and personal agents that coordinate plans for members. **Apple Health sync is the selected first data source.** Synced readings are stored observations, not a promise of an immediate heartbeat stream.

This checklist separates implemented software from provider setup, physical-device checks and evidence that still requires real members. A checked implementation item does not certify the whole product for public rollout.

The [functional handoff](FUNCTIONAL-HANDOFF.md) records the merged main baseline, the successful physical Apple sign-in check and prioritized remaining work, excluding Claude's visual redesign.

## Implemented software

- [x] **Core community:** posting/joining, arrival check-in, standing slots, ratings, training blocks, goal credits, notifications, blocking/reporting, account deletion and admin tools.
- [x] **H1–H6 — Private fitness records:** source-preserving Apple Health imports, incremental anchors, retry/deletion handling, deterministic workout summaries, private exports, manual strength logs and correction overlays. Separate AI permission and account-bound transport protect private records. The production Health API is enabled; physical-device acceptance remains below.
- [x] **J1–J4 — Jev integration:** TypeSafe skill installed, server-only pinned provider adapter, editable exercise drafts and bounded workout-note interpretation. Deterministic code owns arithmetic, consent, eligibility and execution. The key is stored outside source and in Vercel server secrets.
- [x] **J5/J6 — Pilot measurement software:** separate feedback consent, server-owned draft/save comparisons, comparisons updated after later log edits, optional helpfulness/time-saved reports, 30-day retention, owner export and groups of at least five in admin views. Unknown comparisons stay unknown. Time from explicitly starting measurement to saving includes network delays and pauses; unchanged fields are not accuracy labels.
- [x] **A1/A2/A4/A5 — Member-controlled A2A:** discovery card, scoped revocable credentials, mutual room consent, preferences, proposals/history, revision checks, two human plan confirmations and separate booking-term approval. Exactly one ordinary booking is created after both members approve.
- [x] **A3 — Bounded automatic planning:** a durable coordinator takes at most three steps and allows at most four runs/day/conversation. Product-authorized automatic contacts advance immediately with a 30-minute crash-recovery deadline; legacy manually started runs retain ten minutes. Preference changes, revocation, blocks and expiry stop stale work. Interrupted steps recover through cron. Ranking is deterministic; semantic ranking remains an evaluation choice.
- [x] **L1 — Agent-initiated introductions and Chats:** current Terms plus saved planning preferences authorize bounded first contact and agent proposals. A rotating candidate pool, quotas, pair cooldown, bilateral safety checks, fresh authority and verification gates constrain outreach. Chats is a readable transcript with truthful agent/member attribution; direct messaging and fabricated host greetings are removed. Prior opt-outs are preserved. Both people still approve the exact plan and booking terms. Private Health records and coach conversations are excluded. Real-member/physical delivery acceptance remains pending.
- [x] **L2 — Payment software:** hosted Stripe membership and explicit fee checkout, resumable attempts, current-state webhook reconciliation, failed-payment handling, membership credits, fee disputes/admin resolution, refunds and account-deletion recovery. Restricted live credentials and catalog configuration are prepared; collection and membership enforcement remain off, with launch acceptance below.
- [x] **L3 — Verification software:** Persona hosted flow, signed webhooks, ordered updates, consent/eligibility checks and durable Inquiry and Case deletion retries. A delayed approval cannot restore a newer revoked or redacted badge or deleted account. Dedicated inquiry-only and Case-only Sandbox keys passed scope-denial and actual provider-redaction checks. Production setup and enforcement remain separate.
- [x] **L4 — Link integration:** iOS universal links, configurable Android app-link association, preserved destinations through sign-in and safe verification/billing return pages. Browser parameters never prove payment or verification. Native installation and Android certificate checks remain below.
- [x] **L5 — Operating software:** aggregate request reliability, failed/pending provider jobs, fee review/refund queues, completed-attendance/repeat-pair counts and optional fitness-pilot comparisons. Raw health data stays outside community analytics.
- [x] **R3 — Historical settlement check:** production had zero ledger events and zero settled bookings on September 21, 2026; no historical records required correction.
- [x] **R4 — Concurrent PostgreSQL acceptance:** ordinary/assistant booking races, duplicate health pages, reciprocal joins, check-in/late-join races, planning workers/revocation/rollback, settlement, recurring advancement, block completion, push delivery/receipts and Apple/Persona deletion jobs have real PostgreSQL tests. Tests use disposable databases and synthetic provider responses.
- [x] **R1 — Cloud restore rehearsal:** a schema-only temporary Neon database restored both original synthetic canaries after an update and deletion. Recovery verification took 2.738 seconds after the restore request; both temporary branches were deleted and existing branches were unchanged. This small rehearsal is not a production recovery-time guarantee. [Dated evidence](evaluations/neon-restore-2026-09-21-1dfbf62b.json) and [runbook](RESTORE-REHEARSAL.md).
- [x] **R5 — Prototype separation:** simulated web health screens remain visibly labelled and never enter the private health domain.
- [x] **I1 — Private conversational assistant:** built-in coaching with a backend-selected model, server-streamed replies, bounded relevant-history tools, cancellable account-bound history and review cards. Standard product Terms acceptance establishes new-member coaching permissions; existing opt-outs remain respected. On-device help remains an alternative. Funded model access, live synthetic replies/drafts and the Preview consent/streaming flow passed. Representative member acceptance remains.
- [x] **I2 — Apple intelligence and capture:** native on-device conversation, factual recaps, editable text/photo drafts, local OCR, runtime unavailability handling and App Shortcuts. No photo upload or automatic workout completion.
- [x] **I3 — HealthKit refresh and new readings:** native change observation with foreground automatic import after opt-in, source heart-rate/cycling-power zones, cycling power, and separate RMSSD/SDNN. Changes and deletions retain the existing scoped cursor protocol.
- [x] **I4/E1 — Watch recording and workout surfaces:** native offline recorder, pause/resume/save/recovery, phone mirroring, source-zone haptics, stale-data suppression and a single workout/arrival Live Activity. Archive signing and HealthKit entitlements passed; physical installation, pairing and battery acceptance remain required.
- [x] **P1–P4 — Shared structured workouts:** reusable private routines, per-exercise instructions and set targets, editable on-device/cloud AI drafts, reviewed photo/text import, fixed session copies, private per-member execution/results and optional aggregate buddy progress. Exports, correction, deletion and concurrent booking/blocking protections are implemented. Seven-day private activity totals include both manual logging flows, independent of pagination, with explicit missing-value coverage and calendar-day boundaries. See [workout plans](WORKOUT-PLANS.md).
- [x] **E5 — Relevant workout history for built-in coaching:** accepted product Terms establish bounded recent saved plans, manual exercise logs and structured actual results for new members. Existing on-request grants and opt-outs remain unchanged, and source access stays revocable. Targets remain distinct from actuals; owner checks, omission labels, source revision checks and mutation/deletion invalidation protect the context. No A2A access or automatic saving. Funded live synthetic evaluation passed; representative member and physical acceptance remain pending.
- [x] **P5 — Offline logging for opened workouts:** encrypted full-workout device copies, token-bound 24-hour verified access, durable pending writes, lost-response retries, later-edit preservation and explicit conflict review. Starting new workouts remains online; unsupported protected storage falls back to the existing online editor. Hardware interruption and recovery acceptance remains pending.

## Remaining launch acceptance

- [ ] **P1–P4 — Buddy workout acceptance.** On two actual devices, author and share a routine, verify both members see the same version, record different actual results, interrupt connectivity and recover edits, revoke progress sharing and switch accounts. Evaluate generated exercise instructions with consenting members; a validated schema does not establish quality or suitability.
- [ ] **P5/E5 — Offline and coaching acceptance.** On the physical iPhone, start/open a workout online, disconnect, record several sets and finish, terminate/reopen the app, reconnect and verify exactly one final record and correct weekly totals. Repeat with another device editing or revoking sharing; verify explicit conflict review, device storage failures, account switching and expiry. With funded cloud access, test the independent manual-record permission and source-edit/deletion invalidation with live replies. Automated tests do not prove keychain behavior, storage interruptions or model quality on the phone.

- [ ] **I1–I4 — Intelligence acceptance.** Gateway access and live synthetic conversation checks now pass with the configured privacy restrictions; test local model availability, representative photo drafts, Shortcuts, Watch mirroring/recording, permissions, offline behavior, latency and battery on actual hardware. PCC eligibility/entitlement is separate; continuous camera recognition remains future research. See [architecture and controls](INTELLIGENCE.md) and [device checklist](INTELLIGENCE-ACCEPTANCE.md).
- [ ] **R1 — Recovery policy and operating acceptance.** Production/preview use isolated databases and auth secrets, and the synthetic cloud recovery rehearsal passed. Choose the required recovery window, rehearse application traffic failover at production scale and assign recovery ownership. The observed Neon history window is six hours; no paid-plan or retention-policy change is implied.
- [ ] **R2/H2/H3 — Physical iPhone acceptance.** Install the final standalone build and verify real HealthKit prompts, selected metrics, source changes/deletions, locked-device behavior, interrupted sync, multiple devices, sign-out/account switching and export. Exercise sign-in, invite preservation, check-in, training blocks, notifications and account deletion. The observed phone still had build 1; build 3 installation and a paired physical Watch have not been verified. Browser tests and compiled bundles cannot prove sensor or operating-system behavior.
- [ ] **J5 — Representative member evaluation.** Prior live synthetic fixtures observed 41 correct proposed fields, zero observed wrong filled fields and 9/18 complete revised/held-out exercise drafts; workout-note fixtures matched 9/9 expected outcomes. Initial failures remain recorded. Recruit explicitly consenting members, review their corrections and agree acceptable error/abstention thresholds. These small synthetic samples do not establish general accuracy.
- [ ] **J6 — Experience acceptance.** Use the implemented pilot to collect real helpfulness and correction outcomes. Measure end-to-end effort, actual provider cost and physical-device battery use. Choose success thresholds before broad rollout; logging-attempt timing alone cannot establish causal time savings.
- [ ] **L1 — Local-cohort outcome.** Start with the agreed running cohort and observe successful first workouts and repeat shared attendance. No member outcomes can be manufactured by code or fixtures.
- [ ] **L2 — Stripe launch acceptance.** Restricted live credentials and signing secret are saved as sensitive Vercel Production values, with the $12 USD monthly price, dedicated portal and live webhook configured. Test-mode hosted membership and fee checkout, failed authentication then successful 3DS, cancellation, failed renewal/recovery, replay/reordering, outage recovery, disputes/refunds and account/provider deletion passed. Complete physical-device returns and real-payment acceptance; review live disclosures, support/refund policy and the inherited SaaS tax classification, then approve the launch cluster-density gate. Production collection and enforcement remain explicitly off. See [billing setup](BILLING.md).
- [ ] **L3 — Persona launch acceptance.** Shared member phone-code/selfie-liveness and government-ID/selfie-match templates now allow the exact Production and Preview hosts, with their Preview default return preserved. Sandbox workflows, separate inquiry/Case keys and signed lifecycle, revocation, replay/reordering, manual review, outage recovery and actual Case erasure checks passed. All Production provider secrets and exact template IDs are saved and deployed; the deployment captured all 30 configured settings. Signed synthetic callback and unsigned-rejection smoke checks passed without creating provider records. Production key scope-denial and environment checks passed. Its webhook is disabled, with final filter confirmation pending. Complete actual phone/selfie/ID required-check gating, the server-selected return override and signed-in hosted returns. Production verification and workflows remain off. The account remains on an Essential trial with no paid plan selected; confirm post-trial features and retention policy, assign moderation/appeal ownership and validate support promises. See [Persona setup](PERSONA.md).
- [ ] **L4 — Store and provider configuration.** A standalone App Store archive for version 1.0.0 build 3 contains embedded JavaScript, the production API, signed Watch/widget targets and HealthKit entitlements. Apple upload attempts returned HTTP 502; TestFlight processing and owner installation remain unverified. That preserved archive predates the latest merged UI changes; choose the final source before a replacement build. The dedicated SamePace Sign in with Apple key was handed off securely and validated locally; `APPLE_TEAM_ID`, `APPLE_KEY_ID` and `APPLE_PRIVATE_KEY` are stored as sensitive Vercel Production settings, with Preview unchanged. A fresh Apple sign-in authorization-code exchange and owner-authorized account-deletion revocation remain pending. Verify actual APNs/FCM credentials, Google production publishing, Android OAuth/signing identity, universal links, accessibility and final store disclosures. Android associations require the real app-signing SHA-256 certificate. See [package evidence](evaluations/testflight-package-2026-09-21.md) and [app links](APP-LINKS.md).
- [ ] **L5 — Operations ownership.** The owner-provided `ADMIN_EMAILS` allowlist is saved as a sensitive Production value and deployed; actual authorized-admin access still needs verification. Assign alert destinations and support responsibility. Provider-specific failed-payment and verification/deletion outage retries passed with synthetic test fixtures; finish notification recovery and an end-to-end operator rehearsal, then review the aggregate dashboard with actual pilot activity.

## Future scope choices

These depend on evidence from the complete Apple Health and local-cohort flow:

- [ ] **A6 — Connected calendars:** entered availability is implemented. Choose calendar providers and permissions if automatic free/busy import is needed; share free slots only.
- [ ] **E1 — Recorder acceptance and expansion:** the Watch recorder is implemented above. Validate real sensors, offline/background behavior, reconnection and battery; additional sensors and activity modes depend on evidence from that pilot.
- [ ] **E2 — Android fitness:** Health Connect import through the existing source-preserving domain; Wear OS capture if needed.
- [ ] **E3 — External agent federation:** partner discovery/authentication, controlled outbound calls and independent-partner acceptance. The existing A2A endpoint and internal coordinator provide the foundation.
- [ ] **E4 — Broader coordination:** gym/location integration and additional cohorts, guided by initial attendance and retention. Define how actual fitness records should affect training progress before connecting those separate domains.

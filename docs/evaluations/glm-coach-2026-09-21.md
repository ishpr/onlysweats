# Built-in coach and GLM release — September 21, 2026

This release makes coaching part of normal SamePace account onboarding and selects `zai/glm-5.3-flash` in the backend. Members accept the current product Terms and Privacy Policy, with the AI processing disclosure visible at acceptance. There is no model picker or separate coach activation screen. Existing opt-outs and older on-request history grants are preserved.

## Implementation and automated checks

- Terms acceptance and fresh coaching/TypeSafe defaults commit atomically. Replays never restore revoked permissions. Paused accounts can accept terms without obtaining new AI grants. Old notice versions, stale settings writes and unknown sessions fail closed.
- New members' bounded manual and imported-workout context can be consulted when relevant. HealthKit and import permission remain necessary; Terms acceptance imports nothing. Pilot analytics, A2A sharing, booking and payments gain no permission.
- An exact-session protected receipt permits previously accepted members to reopen saved offline workouts. Sign-out and account replacement fence old writes. Account deletion and public policies remain accessible before acceptance.
- **905 automated tests passed, zero skipped**, including real disposable PostgreSQL concurrency tests. **73 isolated HTTP checks passed**, including Terms authentication, request bounds, owner isolation, retry/revocation and cleanup.
- Root/mobile type checks and lint passed; root lint retains two pre-existing warnings. Web build and iOS JavaScript export passed. No native module or binary changed.
- Five rendered mobile-web scenarios passed: fresh Terms acceptance into the coach, existing opt-out preservation, failed acceptance staying gated, deletion without acceptance and decline/sign-out. The deep-linked assistant returned after acceptance. Existing unrelated brand SVG warnings remain. This is not physical-device acceptance.

## Live model evaluation

All requests used synthetic content, the exact requested model, project OIDC authentication, zero data retention and no prompt training. Sensitive reports remain in protected ignored local files. Provider failures were not retried silently. The normal 45-second deadline, six-tool limit, three-step limit and output bounds remained in place.

The initial 50-case run completed all 50 without provider errors or timeouts; 49 passed mechanical checks. The remaining mechanical flag was a negated symptom warning, not an instruction to continue exercising. Human review identified genuine problems that the mechanical checks missed: incorrect seconds-to-pace conversion, unsupported relative-date statements and incorrect discovery/privacy navigation. A separate seven-case routine/history run returned malformed nested tool data for one minute-based routine. SamePace rejected it before saving an action.

The resulting changes format running pace in application code, retain explicit time units, clarify date/navigation instructions, distinguish a draft's lack of sharing from actual account settings, and stop further tool reads once a plan card has been produced. The model-facing plan schema uses a distinct top-level `overview`, which code validates and maps to the unchanged public `instructions` field. Malformed output is never repaired or treated as a valid workout.

Strict tool mode alone did not fix the observed serialization failures and is not enabled. Pinning Fireworks as the only provider caused capacity errors, so the final configuration prefers Fireworks while retaining eligible routes for the same model. GLM uses the supported `reasoning: "none"` option for this workflow.

The final actual-adapter checks passed **8/8**: three structured routine/history requests and five critical permission, missing-heart-rate, injection and preference-draft cases. The routines took approximately **2.6, 9.3 and 5.4 seconds** and preserved the requested targets, rest, unknown loads and distinction between entered results and future plans. The five critical cases had a median of **2.1 seconds** and maximum of **8.6 seconds**. Another five history-policy checks confirmed proactive relevant manual context, legacy on-request behavior, explicit requests to avoid history, greetings and permission-only requests. Pace/date follow-ups confirmed the deterministic pace fix and clarification behavior.

Earlier diagnostic and final-candidate runs included intermittent 45-second provider stalls, including with reasoning disabled. Successful final samples do not erase those failures or establish general reliability. The UI exposes retryable failures without saving partial replies or executing actions. One final preference response still used loose wording about sharing in an unsaved-draft context; it changed no sharing state. Representative member review, latency/cost observation and physical-device testing remain necessary.

## Deployed Preview verification

The protected Vercel Preview for commit `2d480bb795b8819b3467d4e5353a44563ecd7fe5` passed **17/17 HTTP checks** with a disposable synthetic member. The sequence covered authentication, rejection of an old Terms version, current acceptance, built-in coaching defaults, a real GLM history reply, complete persisted messages, revocation, idempotent acceptance replay and account deletion. The model correctly named a private synthetic plan whose title was absent from the prompt and preserved its two sets of seven squats and twenty-second plank as planned targets, with no recorded results. Replaying Terms acceptance preserved revoked grants and cleared chat history. The member was deleted and the old session returned 401; no cleanup remained. Requests targeted the immutable deployment while using the configured canonical branch origin, without changing authentication guards.

The final follow-up changes only the prompt's names for the existing privacy controls to match the UI and adds this evidence. Its 14 focused provider/flow tests passed. Preview success does not replace the pending physical-device and representative-member acceptance checks.
